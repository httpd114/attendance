执行摘要

项目在减少重复核对的同时守住人工确认与可追溯来源两条底线：需求单能说清硬条件与待确认项，每条关键结论能追到来源位置与确认人。试点受四周 32 人时、30 岗位、脱敏只读导出三项硬约束，一期不自动决定派遣资格、不写回三类工具、不直连薪资开票。

系统采用入口层 / 服务层 / 智能体编排层 / 数据模型层四层架构，标准 src-layout 与单向依赖。RAG 用 Markdown 标题切节 + 三路召回 RRF 融合 + 两段式提示词；Agent 用自建轻量 Harness，最多 5 轮决策、9 个工具按角色裁剪，写操作必须回传一次性 HMAC 能力令牌并通过 7 项校验。

正确性靠服务端门禁而非提示词：状态机单一真源放在 attendance_exceptions.agent_state，Agent 权限天花板为 SUBMITTED，复核、驳回、关闭与结算导出不暴露为工具。多租户以用工单位为边界，tenant_id 只从 JWT 注入，管理员复核采用规则预筛 + 人工定性、全量可见可追责。

测试体系覆盖 27 条路由静态守卫、30 条评测用例、Agent 三条轨迹与 8 条硬门禁单测、五类共 39 条场景用例；验收设 G0~G4 五道门禁与 41 条 AC。但上线检查清单 25 项中仍有 12 项 P0 阻塞，Agent 未接入主链路、限流为进程内、注入类规则缺失，当前结论为不具备上线条件。

1. 项目概述

  1.1 业务背景与要解决的问题

实际业务链路来自 f01：客户提需求 → 岗位条件澄清 → 人员安排确认 → 到岗交接 → 反馈。现状 13 步流程中，断点集中在「条件澄清」与「到岗交接」两个交接点之间缺少同步机制，共 5 处（详见 [流程图-01-改造前-现状与典型事件.png](流程图-01-改造前-现状与典型事件.png)）。

典型事件 FSG-SIM-2026-1021-047 把断点串成了可复现的链条：14:07 客户电话临时增加夜班要求（口头 v4、无书面留痕）→ 14:12 群消息同步一句 → 15:40 才补填表格 → 16:05 闭环前人工发现交接单仍挂已确认的 v3 → 16:41 复核关闭，形成 4 条影响清单。其中业务发生时间（14:07）与系统接收时间（15:40）相差 93 分钟，若误把回填时间当作发生时间，「先变更后补录」会被误判为「先有表格后有人改条件」，异常识别顺序整体反转。

  1.2 建设目标

一句话（f00）：在减少重复核对的同时，守住人工确认与可追溯来源两条底线。可验收的两层目标：

  1. 需求单能把硬条件和待确认项说清楚，变更能留下影响清单（f02）。
  2. 每一条关键结论都能追到来源位置和确认人（f42、f45）。

G1 业务效果门禁的三条总口径（不得由单项 AC 通过替代）：完整性（30 个岗位全部列出硬条件与待确认项，每项变更有影响清单）、可追溯性（每条结果关联来源位置与人工复核记录，未锚定项进具名人工队列）、效果口径（处理工时、返工次数、确认完整率三项同时评估，基线冻结前效果浮动按 0 计）。

  1.3 范围与边界

分组范围内明确不做（一期）
场景 A字段抽取、证据锚定、版本比对、双时间轴、影响清单、补单引导、一页缺项清单、人工复核回路写回服务台／台账／文件库、外部消息与执行接口、客户侧工具改造、超出 30 岗位的批量处理
场景 B制度问答、双向确认状态机、证据与合规校验、复核队列自动决定录用／派遣资格、自动算薪、结算直连、开票、设备直连、复杂申诉仲裁
共同底座多租户隔离、提示词版本、规则预筛、全量审计、脱敏导出跨业务线打通、2×2 双向独立一致矩阵、多活容灾、新数据库或重量级编排平台

八条业务红线（不可协商，来自需求分析方案 §4.2）：

编号红线
R-01不自动决定录用或派遣资格，不向真实人员发送安排
R-02口头变更一律视为未确认，须补单并经业务负责人确认后才进交接
R-03AI 不是审批者，权限天花板 SUBMITTED；超时不自动通过，只升级上报
R-04系统建议不覆盖原值、不省略人工确认；不推测客户意图
R-05无法确认版本或关键字段时进人工队列，必要时暂停，不能默认通过
R-06正式结论由授权人员确认；跨企业资料只按明确授权范围访问
R-07试点仅脱敏只读导出，不开放写回
R-08一期只记录并导出结算数据，不直连薪资、不开票

负向清单 X-01~X-05：推测客户意图与自动判投诉责任、自动决定派遣资格、自动审批／超时自动通过／AI 关闭确认单、自动写回与结算、用置信度阈值静默放行未锚定结果。

  1.4 试点硬约束

约束口径
范围一个批次、30 个岗位；脱敏只读导出
资源四周、两名业务骨干、每周投入不超过四小时（约 32 人时）
集成只开放只读导出；写回、外部消息、执行接口均不开放
决策权业务负责人定范围；质量侧保留停止试点权；客户侧确认结果用途
报价口径中档 57 人天、价税合计 243,331 元，固定总价试点（低／中／高三档见 [报价单-FSG-AI-2026-1023-01.md](报价单-FSG-AI-2026-1023-01.md)）

  32 人时内不可能引入新数据库、新编排平台或新标注系统。同行方案中的双时态数据库、标注平台、流程引擎建议只作语义借鉴，不作落地要求。

断点现状表现对应痛点证据等级

  2.2 AI 改造清单与优先级

按 综合分 =（0.35V + 0.25E + 0.25S + 0.15K）× 20 评分，V 业务价值 / E 证据强度 / S 可拦截可恢复 / K 成本友好度；P0 ≥ 80 且承担验收底线或不可逆风险防线，E < 3 分的 P0 项标 G0 条件准入。

序改造项分档阶段设计要点
1AI-01 字段抽取与证据锚定92P0W1–W2六项关键字段 + 原文字符区间，一页缺项清单
2AI-04 制度 RAG 与引用自检88P1W1 复验已具备，待补 chunk_id 命名空间与引用语义校验
3AI-03 双时间轴抽取与拦截85P0W1–W2AI 只抽时间表达式，有效性判定用确定性规则
4AI-02 版本比对与影响清单82P0W2–W3G0 准入，复合键无法唯一匹配即进人工队列
5AI-06 风险预筛（补注入类）81P0W1现 4 类 20 关键词 / 3 正则，缺 injection 类
6AI-08 证据与合规校验80P0W3已具备，是正确性防线
7AI-05 对话式补单助手75P1W3G0 准入，草稿强制「未确认」
8AI-07 Agent 确认闭环接入72P1二期Harness 已具备，尚未挂入主聊天链路
9AI-09 跨团队口径对齐67P2二期基准原始记录未确认
10AI-10 周度复盘归因66P2二期样本不足，只作定性观察

五条改造设计原则：先补证据再上模型；AI 只在判断点生成候选、不在执行点产生后果；每个失败方式都有具名人工接收人；可拦截可恢复优先；不把模型置信度等同于业务风险。

  2.3 改造后流程

见 [流程图-02-改造后-AI数智化.png](流程图-02-改造后-AI数智化.png)：补单留痕 → 双时间轴入库 → 证据锚定 → 关键字段是否全部锚定（否→人工队列）→ 版本双条件判定 → 交接单三要素 → 业务负责人具名确认 → 签收发布 → 差异登记与版本回滚 → 审计留痕与周度复盘；并行接入场景 B 的制度问答、规则预筛、Agent 确认闭环与管理员人工复核。

4. 功能设计

  4.1 场景 A：岗位服务需求单版本交接

六项关键字段：岗位代号、地点、班次、技能条件、版本、确认人。字段契约要求缺失值与未确认值显式区分，不得混为一个空值。

环节设计人工控制点

双时间轴valid_from / valid_to 记业务发生时间，system_received_at 记补录时刻，confirm_status 与时间轴正交独立字段时间戳冲突、读取失败保留快照并提示人工核查

  4.2 场景 B：制度问答与考勤异常双向确认

业务状态机：待确认 → 员工确认／异议 → 管理员复核 → 已确认／已关闭；超时（默认 3 工作日）只升级上报，绝不自动通过。

  • 员工侧：依据租户制度知识库流式提问，答案带引用编号；对自己的考勤异常（迟到、下班缺卡、加班时长争议）确认或提出异议，补齐证据材料。
  • Agent 侧：材料校验 → 制度合规校验 → 建立确认单草稿 → 提交至复核队列，止于 SUBMITTED。
  • 管理员侧：在后台人工复核、驳回、关闭，导出结算清单；导出仅 CSV，不直连薪资、不开票，界面文案不暗示已发起付款。
  • 当前实现状态：完整后台复核队列尚未实现，CLOSED / REJECTED 跃迁与 close_case / reject_case 工具未定义，超时自动升级的定时作业未找到实现（详见第 13 章）。

  4.3 管理后台

采用用户确认的口径：规则预筛 + 人工复核、管理员建号、租户隔离、全量可见（审计要求，能追责）。

5. AI 能力详细设计

  5.1 RAG 引擎（core/rag_engine.py）

环节设计
切节TextChunker.split() 先按行首 # 切节、绝不跨节合并；节内超 chunk_size=500 再按行细分（overlap=50），min_chunk_len=30 过滤。PDF 每页插伪标题 # 第 N 页 降级。纯滑窗会把多章节搅进同一块导致答案串项
召回三路各取 20 候选：jieba 词级 BM25、字符二元组 BM25（先剥 markdown／标点）、FAISS 向量（IndexFlatIP + L2 归一化 = 余弦）
融合RRF score(d)=Σ 1/(rrf_k + rank)，rrf_k=60，取 top_k=3；结果带引用编号、章节、片段与 hit_by 三路标记
提示词两段式：MANDATORY_RULES 六条硬规则代码写死且永远在最前（只依据原文、[n] 引用、不得改号、未覆盖须拒答、数字原文引用）；DEFAULT_PROMPT_BODY 管理员可编辑，存 prompt_templates
引用自检validate_citations() 机械校验：提取 \[n\]、查越界、判有无引用；REFUSAL_PATTERNS 5 条拒答白名单命中即 is_refusal=True。抓不住「编号没越界但指错块」
历史截断history_rounds=6（12 条）+ history_char_budget=3000 双重上限，超出从最早丢；引用编号仅本轮有效
离线降级EMBED_PROVIDER=hash 时整条向量路关闭、退化为纯 BM25（哈希向量无语义会污染 Top3）；无 LLM 配置时 MockLLM。演示版 MockLLM 会回显提示词前 300 字，属已登记缺陷 D-02

  5.2 Agent Harness（core/agent_loop.py）

一轮 = 一次模型决策 + 串行执行该批 tool_calls + 一次性回填，硬上限 max_rounds=5。第 5 轮仍调工具时不发起第 6 次决策，用规则模板 _finalize() 收敛并写 audit_logs(action="agent_round_limit")。

轮典型动作
1批量只读：list_my_exceptions、get_exception_detail、lookup_policy、get_case_state
2validate_evidence → 签发凭证
3create_confirmation_draft（写，回传凭证）
4validate_policy_compliance → 签发新凭证
5submit_confirmation → 达 SUBMITTED

系统消息每轮重建，运行时状态卡由服务端从数据库生成，不让模型靠多轮历史推断进度（历史会被裁剪、压缩、注入污染）。tools_for(role) 在构造请求前裁剪：员工 9 个工具，管理员只读 4 个；tenant_id / user_id / role 不进工具 schema，从 JWT 注入。

  5.3 能力门禁（core/agent_gate.py）

CapabilityGate 用 HMAC 签发一次性凭证，ttl=300s，claims 共 10 字段：jti, iat, exp, tenant_id, user_id, action, bind_scope, params_hash, policy_version, prompt_version；params_hash=canonical_hash(normalizer(params))，bind_scope 为 evidence（5 字段归一化）或 case（仅 case_id）。

7 项校验（固定顺序，jti 消费放最后防 DoS）：

#校验拒绝码
1签名 hmac.compare_digestERR_TOKEN_INVALID
2有效期 expERR_TOKEN_EXPIRED
3身份与租户ERR_TOKEN_SCOPE
4动作匹配ERR_TOKEN_ACTION
5bind_scope + params_hash 参数摘要ERR_PARAMS_MISMATCH
6ALLOWED_STATES + db.get_state() 状态机ERR_ILLEGAL_TRANSITION
7jti 原子一次消费（INSERT OR IGNORE，等价 SETNX）ERR_TOKEN_USED

写工具由 CapabilityGate.protect 包装；缺凭证时 ERR_CAPABILITY_REQUIRED 单独拦截并写 gate_rejected 审计。正确性靠服务端门禁，不靠系统提示词——提示词让模型「通常不跳步」，门禁让「跳步绝不产生业务后果」。

AGENT_GATE_SECRET 未配置时进入 dev_mode，密钥固定派生为 sha256(b"attendance-agent-dev-only")，仅限演示，生产必须注入。

  5.4 规则预筛（core/audit_rules.py）

4 类共 20 个关键词：fraud（F01–F09，9 条）、bypass（B01–B06，6 条）、sensitive（S01–S03，3 条）、advice（A01–A02，2 条）；权重 3/2/1，同类别只留最高权重一条。3 条正则：改(大|高|多)一点、(多|加)报\s*\d、帮(我)?(垫|垫付|先付)。

  • 阈值 should_flag = any(h.weight >= 2)，低危词不推预警。
  • 只扫员工提问，不扫助手回答（助手复述「虚报」「超标」是正常的，连回答一起扫会让预警量爆炸）。
  • 命中写 audit_flags(status="suspected")，系统永不自动判违规；管理员复核后才定性。
  • 待补：injection 类规则。当前「忽略之前的指令」「扮演」等注入句会静默放行、审计页查不到（缺陷 D-01、上线清单 P0）。

  5.5 明确不做的 AI 改造

X-01 推测客户意图／自动判投诉责任（f54 禁止）；X-02 自动决定录用或派遣资格；X-03 自动审批、超时自动通过、AI 关闭确认单；X-04 自动写回三类工具、直连薪资／开票；X-05 用置信度阈值静默放行未锚定结果。

7. 接口设计

  7.1 鉴权

JWT_ALGORITHM=HS256、JWT_EXPIRE_HOURS=12；载荷固定 sub(user_id)、tid(tenant_id)、rol(role)、unm(username)、iat、exp、jti。登录写 httponly + samesite=lax Cookie（max_age=43200），也支持 Authorization: Bearer。

get_current_user() 每次请求回查 DB 校验 is_active 与 user["tenant_id"]==payload["tid"]，且不信任 JWT 里的角色（防令牌跨租户复用、停用后旧令牌立即失效）。require_user() 任意已登录；require_admin() 校验 role=="admin"。tenant_id 只从 JWT 注入，绝不接受请求体／查询参数。

  7.4 SSE 协议

帧格式 event: X\ndata: {json}\n\n（ensure_ascii=False）；响应头 Cache-Control: no-cache、Connection: keep-alive、X-Accel-Buffering: no。

meta → status(retrieving) → citations → status(generating) → delta* → done
任一环节失败 → error（此后不再发其他事件）
  • meta 实际字段为 {session_id, message_id, is_new_session}（注意 api.md 中写的 {session_id, request_id} 与代码有出入，以代码为准）。
  • done 带 usage / latency_ms / citation_check。
  • 算法层 RAGEngine.stream_chat() 只发 citations → delta* → done，meta / status 由接口层补；同步生成器经 aiter_sync_gen() + 8 线程池跨线程队列搬运。
  • 流中断时前端必须标注「回答未完成，请勿据此办理」并给出重试／转人工入口，不允许空白气泡或永久转圈。

  7.5 Agent 工具 schema 规范

9 个工具：只读 4 个（list_my_exceptions、get_exception_detail、lookup_policy、get_case_state），校验签发 2 个（validate_evidence、validate_policy_compliance），受门禁写操作 2 个（create_confirmation_draft、submit_confirmation），安全动作 1 个（escalate_case）。

admin_review / export_settlement / close_case / reject_case 根本不定义——不暴露就不可能调用。工具 schema 不含身份字段。

8. 安全与权限设计

  8.1 多租户隔离

以用工单位为隔离边界；派遣公司跨租户只读监管；员工仅本人数据。所有 AdminDB 对外方法第一个位置参数固定 tenant_id，SQL WHERE 以 tenant_id 打头；AgentDB 查询带 tenant_id=? AND user_id=?；KnowledgeBase._indexes[tenant_id] 每租户独立索引；会话恢复先判租户再判归属，非管理员只能读本人会话；启动时 _check_tenant_orphans() 自检孤儿租户分区。跨租户访问一律 403／404 且不泄露资源存在性（AC-27 遍历全部 27 条路由验证）。

  8.2 四层能力边界

层机制保证
L1 工具暴露面按角色裁剪 tools 白名单管理动作根本不在员工 Agent 工具列表
L2 服务端状态机 + 能力令牌7 项校验的一次性 HMAC 凭证跳步、伪造、复用、参数漂移、跨租户均不产生业务后果
L3 幂等 + 全量审计幂等键、决策日志、工具日志、gate_rejected 标记可回滚、可追责、可观测
L4 系统提示词强制段代码写死 + 运行时状态卡 + 可编辑正文只改善效率与话术，不承担正确性

  8.3 注入防御与内容安全

现有：强制段不可被正文段覆盖；只扫提问不扫回答；拒答白名单；门禁独立于提示词。

待补（P0）：injection 类预筛规则，覆盖「忽略之前的指令」「忽略上述规则」「系统提示词」「扮演」等特征；间接注入（员工备注、上传的制度文档）埋点检测；回复不复述规则原文、不泄露 token；提示词版本回滚演练（AC-28、AC-29）。

  8.4 限流与配额

RateLimiter(max_calls=20, window_sec=60) 为进程内滑动窗口（dict[key→list[float]] + threading.Lock），键 user:{user.id}，超限 42901。实测前 20 次 200、第 21 次 429。多 worker 不共享，部署侧需换 Redis（接口 check(key) -> bool 已按可替换设计）。待补：租户日调用上限、月度 token／费用告警、超额不发起 LLM 调用（NFR-06 / AC-38）。

  8.5 密钥与 dev_mode

JWT_SECRET 默认 dev-only-change-me-in-production；AGENT_GATE_SECRET 缺失时进入 dev_mode。config/default.yaml 声明「缺失必需密钥即拒绝启动」，但代码内强校验尚未实现，仅 scripts/deploy.sh 做启动前兜底检查。生产须由密钥管理服务注入，dev_mode 禁用，TLS 由反代终止（AC-34）。

10. 部署与运维

  10.1 环境与依赖

pyproject.toml 声明 Python >=3.11；CI 只在 3.13 验证（历史坑：numpy==2.5.3 要求 ≥3.12，3.11 失败）。3.11 环境建议 pip install -e . 自行解析依赖，不用固定 requirements.txt。config/default.yaml 当前不会被程序自动加载，全部配置走环境变量。

  10.2 启动

export PYTHONPATH="$PWD/src"
python -m uvicorn attendance_agent.main:app --host 127.0.0.1 --port 8000
# 或：python -m attendance_agent.main

关键环境变量：DB_PATH / DOC_PATH / INDEX_DIR、JWT_SECRET、AGENT_GATE_SECRET、LLM_BASE_URL / LLM_API_KEY / LLM_MODEL、EMBED_PROVIDER、HOST / PORT。scripts/deploy.sh 启动前预检必需密钥。新库须先跑 scripts/migrate.py 补 tenant_id / flag_status 列。

  10.3 自检与 CI

PYTHON=<已装依赖解释器> bash scripts/build.sh 共 7 步：全量 Python 语法检查、运行依赖预检、27 条路由完整性、30 条评测用例集合法性、核心单测、Agent 三轨迹 + 8 条硬门禁单测、页面与静态资源检查。GitHub Actions 在 Python 3.13 上运行同一套自检（早期 run 42150647198 success）。

  10.4 备份与回滚

SQLite 用 Connection.backup() 在 WAL 有写入时做一致性备份，目标每日自动、异地保留 ≥7 天；每个迁移须有 down 脚本或书面规定「唯一回退路径为备份恢复」并写入 runbook。上线后 30 分钟内 5xx 率超阈值须能按书面阈值、决策人、逐步命令完成回滚演练（AC-35、AC-36、AC-41）。
