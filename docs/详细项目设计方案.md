## 1. 项目概述

### 1.1 业务背景与要解决的问题

实际业务链路来自 f01：**客户提需求 → 岗位条件澄清 → 人员安排确认 → 到岗交接 → 反馈**。现状 13 步流程中，断点集中在「条件澄清」与「到岗交接」两个交接点之间缺少同步机制，共 5 处（详见 [流程图-01-改造前-现状与典型事件.png](流程图-01-改造前-现状与典型事件.png)）。

典型事件 `FSG-SIM-2026-1021-047` 把断点串成了可复现的链条：14:07 客户电话临时增加夜班要求（口头 v4、无书面留痕）→ 14:12 群消息同步一句 → 15:40 才补填表格 → 16:05 闭环前人工发现交接单仍挂已确认的 v3 → 16:41 复核关闭，形成 4 条影响清单。其中业务发生时间（14:07）与系统接收时间（15:40）相差 93 分钟，若误把回填时间当作发生时间，「先变更后补录」会被误判为「先有表格后有人改条件」，异常识别顺序整体反转。

### 1.2 建设目标

一句话（f00）：**在减少重复核对的同时，守住人工确认与可追溯来源两条底线**。可验收的两层目标：

1. 需求单能把硬条件和待确认项说清楚，变更能留下影响清单（f02）。
2. 每一条关键结论都能追到来源位置和确认人（f42、f45）。

G1 业务效果门禁的三条总口径（不得由单项 AC 通过替代）：**完整性**（30 个岗位全部列出硬条件与待确认项，每项变更有影响清单）、**可追溯性**（每条结果关联来源位置与人工复核记录，未锚定项进具名人工队列）、**效果口径**（处理工时、返工次数、确认完整率三项同时评估，基线冻结前效果浮动按 0 计）。

### 1.3 范围与边界

| 分组 | 范围内 | 明确不做（一期） |
|---|---|---|
| 场景 A | 字段抽取、证据锚定、版本比对、双时间轴、影响清单、补单引导、一页缺项清单、人工复核回路 | 写回服务台／台账／文件库、外部消息与执行接口、客户侧工具改造、超出 30 岗位的批量处理 |
| 场景 B | 制度问答、双向确认状态机、证据与合规校验、复核队列 | 自动决定录用／派遣资格、自动算薪、结算直连、开票、设备直连、复杂申诉仲裁 |
| 共同底座 | 多租户隔离、提示词版本、规则预筛、全量审计、脱敏导出 | 跨业务线打通、2×2 双向独立一致矩阵、多活容灾、新数据库或重量级编排平台 |

**八条业务红线**（不可协商，来自需求分析方案 §4.2）：

| 编号 | 红线 |
|---|---|
| R-01 | 不自动决定录用或派遣资格，不向真实人员发送安排 |
| R-02 | 口头变更一律视为未确认，须补单并经业务负责人确认后才进交接 |
| R-03 | AI 不是审批者，权限天花板 `SUBMITTED`；超时不自动通过，只升级上报 |
| R-04 | 系统建议不覆盖原值、不省略人工确认；不推测客户意图 |
| R-05 | 无法确认版本或关键字段时进人工队列，必要时暂停，不能默认通过 |
| R-06 | 正式结论由授权人员确认；跨企业资料只按明确授权范围访问 |
| R-07 | 试点仅脱敏只读导出，不开放写回 |
| R-08 | 一期只记录并导出结算数据，不直连薪资、不开票 |

**负向清单 X-01~X-05**：推测客户意图与自动判投诉责任、自动决定派遣资格、自动审批／超时自动通过／AI 关闭确认单、自动写回与结算、用置信度阈值静默放行未锚定结果。

### 1.4 试点硬约束

| 约束 | 口径 |
|---|---|
| 范围 | 一个批次、30 个岗位；脱敏只读导出 |
| 资源 | 四周、两名业务骨干、每周投入不超过四小时（约 32 人时） |
| 集成 | 只开放只读导出；写回、外部消息、执行接口均不开放 |
| 决策权 | 业务负责人定范围；质量侧保留停止试点权；客户侧确认结果用途 |
| 报价口径 | 中档 57 人天、价税合计 243,331 元，固定总价试点（低／中／高三档见 [报价单-FSG-AI-2026-1023-01.md](报价单-FSG-AI-2026-1023-01.md)） |

> 32 人时内不可能引入新数据库、新编排平台或新标注系统。同行方案中的双时态数据库、标注平台、流程引擎建议只作语义借鉴，不作落地要求。

## 2. 现状分析与改造映射

### 2.1 五处断点与 12 条痛点

| 断点 | 现状表现 | 对应痛点 | 证据等级 |
|---|---|---|---|
| 1 | 回填时间被当作业务发生时间（93 分钟口径差） | P-05 | A |
| 2 | 按文件名／时间戳猜「最新版」，缺双条件判定 | P-04 | A |
| 3 | 交接单引用旧技能要求（v3 vs 口头 v4、2 字段差异） | P-02、P-03 | C / A |
| 4 | 到岗交接只发「已处理」，缺最新版本／未确认项／截止时间 | P-01、P-06 | B / A |
| 5 | 审计只留摘要、只改模板不核效果 | P-07、P-10 | A / B |

完整 12 条痛点（P-01 口头变更无留痕、P-02 交接单引用旧版本、P-03 长摘要而非缺项清单、P-04 版本靠文件名猜、P-05 时间口径混淆、P-06 缺兜底默认通过、P-07 审计只留摘要、P-08 跨团队口径不一致、P-09 重复澄清、P-10 误报漏报无闭环、P-11 考勤异常缺双向确认、P-12 生产安全与回滚阻塞）见《需求分析方案 v1.0》§2。

### 2.2 AI 改造清单与优先级

按 `综合分 =（0.35V + 0.25E + 0.25S + 0.15K）× 20` 评分，V 业务价值 / E 证据强度 / S 可拦截可恢复 / K 成本友好度；P0 ≥ 80 且承担验收底线或不可逆风险防线，**E < 3 分的 P0 项标 G0 条件准入**。

| 序 | 改造项 | 分 | 档 | 阶段 | 设计要点 |
|---|---|---|---|---|---|
| 1 | AI-01 字段抽取与证据锚定 | 92 | P0 | W1–W2 | 六项关键字段 + 原文字符区间，一页缺项清单 |
| 2 | AI-04 制度 RAG 与引用自检 | 88 | P1 | W1 复验 | 已具备，待补 `chunk_id` 命名空间与引用语义校验 |
| 3 | AI-03 双时间轴抽取与拦截 | 85 | P0 | W1–W2 | AI 只抽时间表达式，有效性判定用确定性规则 |
| 4 | AI-02 版本比对与影响清单 | 82 | P0 | W2–W3 | **G0 准入**，复合键无法唯一匹配即进人工队列 |
| 5 | AI-06 风险预筛（补注入类） | 81 | P0 | W1 | 现 4 类 20 关键词 / 3 正则，缺 `injection` 类 |
| 6 | AI-08 证据与合规校验 | 80 | P0 | W3 | 已具备，是正确性防线 |
| 7 | AI-05 对话式补单助手 | 75 | P1 | W3 | **G0 准入**，草稿强制「未确认」 |
| 8 | AI-07 Agent 确认闭环接入 | 72 | P1 | 二期 | Harness 已具备，**尚未挂入主聊天链路** |
| 9 | AI-09 跨团队口径对齐 | 67 | P2 | 二期 | 基准原始记录未确认 |
| 10 | AI-10 周度复盘归因 | 66 | P2 | 二期 | 样本不足，只作定性观察 |

**五条改造设计原则**：先补证据再上模型；AI 只在判断点生成候选、不在执行点产生后果；每个失败方式都有具名人工接收人；可拦截可恢复优先；不把模型置信度等同于业务风险。

### 2.3 改造后流程

见 [流程图-02-改造后-AI数智化.png](流程图-02-改造后-AI数智化.png)：补单留痕 → 双时间轴入库 → 证据锚定 → 关键字段是否全部锚定（否→人工队列）→ 版本双条件判定 → 交接单三要素 → 业务负责人具名确认 → 签收发布 → 差异登记与版本回滚 → 审计留痕与周度复盘；并行接入场景 B 的制度问答、规则预筛、Agent 确认闭环与管理员人工复核。

## 3. 总体架构设计

### 3.1 四层架构

| 层 | 实现 | 职责 |
|---|---|---|
| 入口层 | `main.py`（FastAPI）、`core/auth.py` | JWT 鉴权、SSE 流、统一中文错误体、限流、页面渲染 |
| 服务层 | `core/kb.py`、`admin_db.py`、`agent_db.py`、`audit_rules.py` | 知识库、会话与用户、确认单状态、审计标记、动作日志 |
| 智能体编排层 | `core/agent_loop.py`、`agent_gate.py`、`agent_tools.py`、`agent_prompt.py` | 模型决策循环、能力令牌门禁、工具 schema 与执行、强制提示词 |
| 数据模型层 | SQLite（WAL）+ FAISS 内存索引 + embedding BLOB | 会话、消息、切片与向量、审计日志、Agent 决策日志 |

FAISS 索引是**内存派生**的，重启后从 `kb_chunks.embedding` BLOB 重建，删除文档无需再调 embedding API。设计演进方向为 PostgreSQL + pgvector、Redis 共享限流、对象存储放附件；一期不引入。

### 3.2 代码分层与目录结构

标准 Python 工程骨架（src-layout，`pyproject.toml` 中 `where=["src"]`）：

```text
attendance/
├── src/attendance_agent/
│   ├── main.py                 # FastAPI 入口，27 条路由，不 import 任何 agent_* 模块
│   ├── core/
│   │   ├── auth.py             # bcrypt / PyJWT / require_user / require_admin
│   │   ├── admin_db.py         # 租户、用户、知识库、提示词、审计标记、动作日志
│   │   ├── agent_db.py         # 异常、证据、确认单、状态事件、决策日志、凭证消费

│   │   ├── agent_tools.py      # 9 个工具 schema、角色裁剪、执行器
│   │   ├── agent_loop.py       # 自建轻量 Harness、GLMClient、ScriptedLLM
```

依赖单向：`main.py → core.* + utils.paths`；`core/` 只依赖同层与 `utils.*`，**不得反向 import main**；`utils/paths.py` 零业务依赖。所有包内导入用相对导入，禁止重构前那种 `cd src/attendance_agent && python main.py` 的平铺执行方式。

### 3.3 技术选型

| 领域 | 选型 | 理由 |
|---|---|---|
| Web 框架 | FastAPI + Uvicorn | SSE 原生支持、依赖注入便于 `require_user` / `require_admin` |
| 存储 | SQLite（`journal_mode=WAL`，三个 DB 类共用一个文件，`threading.Lock`） | 试点 32 人时内零运维成本 |
| 检索 | BM25（词 + 中文字符二元组）+ FAISS `IndexFlatIP` 向量，RRF 融合 | 纯关键词在中文短问题上召回不稳，纯向量在 hash 降级时不可信 |
| 大模型 | 智谱 `glm-4-flash`；`embedding-2`（1024 维） | 中文效果好、成本低；`temperature=0.1`、`max_tokens=800`、`timeout=60` |
| 鉴权 | PyJWT HS256 + bcrypt（rounds=12） | 无外部依赖，停用账号每次请求回查 DB 立即失效 |
| Agent | 自建轻量 Harness | 9 工具 5 轮用不上状态图／checkpoint；框架越薄越易插硬门禁与逐轮审计 |
| 前端 | Jinja2 模板 + 原生 JS（EventSource 消费 SSE） | 无构建链，便于演示与审计 |

| 形态 | 入口 | 用途 |
|---|---|---|
| 本地开发 | `PYTHONPATH=src python -m uvicorn attendance_agent.main:app --host 127.0.0.1 --port 8000` | 完整功能含管理后台 |

## 4. 功能设计

### 4.1 场景 A：岗位服务需求单版本交接

**六项关键字段**：岗位代号、地点、班次、技能条件、版本、确认人。字段契约要求**缺失值与未确认值显式区分，不得混为一个空值**。

| 环节 | 设计 | 人工控制点 |
|---|---|---|
| 变更登记 | 三入口统一接入；超时升级业务负责人并暂停该岗位交接，不默认放行 | HC-A 口头变更是否成立 |
| 双时间轴 | `valid_from` / `valid_to` 记业务发生时间，`system_received_at` 记补录时刻，`confirm_status` 与时间轴正交独立字段 | 时间戳冲突、读取失败保留快照并提示人工核查 |
| 证据锚定 | 每条抽取结果携带 `source_ref`（文件路径 + 原文字符区间）；未锚定一律进人工队列，不写交接单 | 清单字段范围由林亦舟、傅景书面确认 |
| 版本判定 | **有效期 AND 确认状态**双条件；文件名、戳记不参与；作废保留 `invalidate_reason` | 责任归属不交给模型 |
| 影响清单 | 输出岗位、字段、旧值／新值、发生节点、影响对象；只给候选不判责 | 变更成立与影响接受由业务负责人、协调员确认 |
| 交接单 | 最新版本 + 未确认项 + 截止时间，**三项缺一不发** | 业务负责人具名确认（f25） |
| 兜底 | 无统一编号时用「岗位代号＋批次＋地点＋班次」复合键试匹配，仍无法唯一匹配即进人工队列，绝不猜测配对 | 具名接收人由质量侧指定 |

### 4.2 场景 B：制度问答与考勤异常双向确认

**业务状态机**：`待确认 → 员工确认／异议 → 管理员复核 → 已确认／已关闭`；超时（默认 3 工作日）**只升级上报，绝不自动通过**。

- 员工侧：依据租户制度知识库流式提问，答案带引用编号；对自己的考勤异常（迟到、下班缺卡、加班时长争议）确认或提出异议，补齐证据材料。
- Agent 侧：材料校验 → 制度合规校验 → 建立确认单草稿 → 提交至复核队列，止于 `SUBMITTED`。
- 管理员侧：在后台人工复核、驳回、关闭，导出结算清单；导出仅 CSV，不直连薪资、不开票，界面文案不暗示已发起付款。
- 当前实现状态：完整后台复核队列尚未实现，`CLOSED` / `REJECTED` 跃迁与 `close_case` / `reject_case` 工具未定义，超时自动升级的定时作业未找到实现（详见第 13 章）。

### 4.3 管理后台

采用用户确认的口径：**规则预筛 + 人工复核、管理员建号、租户隔离、全量可见（审计要求，能追责）**。

| 模块 | 能力 | 人工点 |
|---|---|---|
| 用户管理 | 建号、停用、改密，`require_admin`；不开放注册 | HC-04 |
| 知识库 | 多文档上传（10 MB 上限）、切片质量页、显式 POST 重建索引 | HC-02 |
| 提示词 | 强制段代码锁定、正文段可编辑、按租户版本管理；回滚 = 生成新版本而非改历史行 `is_active` | HC-03 |
| 对话审计 | 分页列表（每页 30）、JOIN 会话与用户、最新标记子查询；管理员判 `confirmed` / `rejected` | HC-01 |
| 审计日志 | 每次管理／门禁动作一行，含动作、目标、详情、操作人、IP | 全量可见 |

**六处人工确认点**：HC-01 对话审计复核、HC-02 知识库上传／重建、HC-03 提示词发布／回滚、HC-04 建号／停用／改密、HC-05 确认单复核／关闭、HC-06 上线放行签字。**HC-01 / HC-03 / HC-05 是最小必做三处**，缺任何一处不得宣称具备人工回路。

## 5. AI 能力详细设计

### 5.1 RAG 引擎（`core/rag_engine.py`）

| 环节 | 设计 |
|---|---|
| 切节 | `TextChunker.split()` 先按行首 `#` 切节、**绝不跨节合并**；节内超 `chunk_size=500` 再按行细分（`overlap=50`），`min_chunk_len=30` 过滤。PDF 每页插伪标题 `# 第 N 页` 降级。纯滑窗会把多章节搅进同一块导致答案串项 |
| 召回 | 三路各取 20 候选：jieba 词级 BM25、字符二元组 BM25（先剥 markdown／标点）、FAISS 向量（`IndexFlatIP` + L2 归一化 = 余弦） |
| 融合 | RRF `score(d)=Σ 1/(rrf_k + rank)`，`rrf_k=60`，取 `top_k=3`；结果带引用编号、章节、片段与 `hit_by` 三路标记 |
| 提示词 | 两段式：`MANDATORY_RULES` 六条硬规则代码写死且永远在最前（只依据原文、`[n]` 引用、不得改号、未覆盖须拒答、数字原文引用）；`DEFAULT_PROMPT_BODY` 管理员可编辑，存 `prompt_templates` |
| 引用自检 | `validate_citations()` 机械校验：提取 `\[n\]`、查越界、判有无引用；`REFUSAL_PATTERNS` 5 条拒答白名单命中即 `is_refusal=True`。**抓不住「编号没越界但指错块」** |
| 历史截断 | `history_rounds=6`（12 条）+ `history_char_budget=3000` 双重上限，超出从最早丢；引用编号仅本轮有效 |
| 离线降级 | `EMBED_PROVIDER=hash` 时**整条向量路关闭、退化为纯 BM25**（哈希向量无语义会污染 Top3）；无 LLM 配置时 `MockLLM`。演示版 MockLLM 会回显提示词前 300 字，属已登记缺陷 D-02 |

### 5.2 Agent Harness（`core/agent_loop.py`）

**一轮 = 一次模型决策 + 串行执行该批 `tool_calls` + 一次性回填**，硬上限 `max_rounds=5`。第 5 轮仍调工具时不发起第 6 次决策，用规则模板 `_finalize()` 收敛并写 `audit_logs(action="agent_round_limit")`。

| 轮 | 典型动作 |
|---|---|
| 1 | 批量只读：`list_my_exceptions`、`get_exception_detail`、`lookup_policy`、`get_case_state` |
| 2 | `validate_evidence` → 签发凭证 |
| 3 | `create_confirmation_draft`（写，回传凭证） |
| 4 | `validate_policy_compliance` → 签发新凭证 |
| 5 | `submit_confirmation` → 达 `SUBMITTED` |

系统消息每轮重建，**运行时状态卡由服务端从数据库生成**，不让模型靠多轮历史推断进度（历史会被裁剪、压缩、注入污染）。`tools_for(role)` 在构造请求前裁剪：员工 9 个工具，管理员只读 4 个；`tenant_id` / `user_id` / `role` 不进工具 schema，从 JWT 注入。

### 5.3 能力门禁（`core/agent_gate.py`）

`CapabilityGate` 用 HMAC 签发一次性凭证，`ttl=300s`，claims 共 10 字段：`jti, iat, exp, tenant_id, user_id, action, bind_scope, params_hash, policy_version, prompt_version`；`params_hash=canonical_hash(normalizer(params))`，`bind_scope` 为 `evidence`（5 字段归一化）或 `case`（仅 `case_id`）。

**7 项校验（固定顺序，`jti` 消费放最后防 DoS）**：

| # | 校验 | 拒绝码 |
|---|---|---|
| 1 | 签名 `hmac.compare_digest` | `ERR_TOKEN_INVALID` |
| 2 | 有效期 `exp` | `ERR_TOKEN_EXPIRED` |
| 3 | 身份与租户 | `ERR_TOKEN_SCOPE` |
| 4 | 动作匹配 | `ERR_TOKEN_ACTION` |
| 5 | `bind_scope` + `params_hash` 参数摘要 | `ERR_PARAMS_MISMATCH` |
| 6 | `ALLOWED_STATES` + `db.get_state()` 状态机 | `ERR_ILLEGAL_TRANSITION` |
| 7 | `jti` 原子一次消费（`INSERT OR IGNORE`，等价 SETNX） | `ERR_TOKEN_USED` |

写工具由 `CapabilityGate.protect` 包装；缺凭证时 `ERR_CAPABILITY_REQUIRED` 单独拦截并写 `gate_rejected` 审计。**正确性靠服务端门禁，不靠系统提示词**——提示词让模型「通常不跳步」，门禁让「跳步绝不产生业务后果」。

`AGENT_GATE_SECRET` 未配置时进入 `dev_mode`，密钥固定派生为 `sha256(b"attendance-agent-dev-only")`，**仅限演示，生产必须注入**。

### 5.4 规则预筛（`core/audit_rules.py`）

4 类共 20 个关键词：`fraud`（F01–F09，9 条）、`bypass`（B01–B06，6 条）、`sensitive`（S01–S03，3 条）、`advice`（A01–A02，2 条）；权重 3/2/1，同类别只留最高权重一条。3 条正则：`改(大|高|多)一点`、`(多|加)报\s*\d`、`帮(我)?(垫|垫付|先付)`。

- 阈值 `should_flag = any(h.weight >= 2)`，低危词不推预警。
- **只扫员工提问，不扫助手回答**（助手复述「虚报」「超标」是正常的，连回答一起扫会让预警量爆炸）。
- 命中写 `audit_flags(status="suspected")`，**系统永不自动判违规**；管理员复核后才定性。
- 待补：`injection` 类规则。当前「忽略之前的指令」「扮演」等注入句会静默放行、审计页查不到（缺陷 D-01、上线清单 P0）。

### 5.5 明确不做的 AI 改造

X-01 推测客户意图／自动判投诉责任（f54 禁止）；X-02 自动决定录用或派遣资格；X-03 自动审批、超时自动通过、AI 关闭确认单；X-04 自动写回三类工具、直连薪资／开票；X-05 用置信度阈值静默放行未锚定结果。

## 6. 数据设计

### 6.1 存储总体

三个 DB 类（`ChatDB` / `AdminDB` / `AgentDB`）共用同一 SQLite 文件，均 `threading.Lock` + `PRAGMA journal_mode=WAL`。默认路径由 `utils/paths.py` 统一解析：`DEFAULT_DB_PATH=PROJECT_ROOT/data/chat.db`、`DEFAULT_DOC_PATH=data/报销制度.md`、`INDEX_DIR=data/.rag_cache`，可用 `DB_PATH` / `DOC_PATH` / `INDEX_DIR` 环境变量覆盖。

### 6.2 表清单（按域分组）

| 域 | 表 | 关键字段 |
|---|---|---|
| 租户与账号 | `tenants`、`users` | `UNIQUE(tenant_id, username)`、`role`、`is_active`、`password_hash`、`last_login_at` |
| 会话 | `conversations`、`messages` | `messages` 含 `citations`、`citation_check`、`status`、`error_code`、tokens、`latency_ms`；索引 `idx_messages_conv_time` |
| 知识库 | `kb_documents`、`kb_chunks`、`prompt_templates` | `kb_chunks.embedding` BLOB（float32 × 1024 = 4 KB/块）、`section`、`embed_model`；提示词 `version` / `is_active` |
| 审计 | `audit_flags`、`audit_logs` | 标记 `status='suspected'` → `confirmed`/`rejected`；日志含 actor、action、target、detail、IP |
| 业务 | `attendance_exceptions`、`evidence_files`、`confirmation_cases`、`case_events` | `attendance_exceptions.agent_state` 是状态单一真源；`confirmation_cases` 有 `UNIQUE(tenant_id, exception_id, declaration)` |
| 决策日志 | `agent_rounds`、`agent_tool_calls` | 一轮一行 / 一次调用一行；`UNIQUE(session_id, round_no)`；含 `prompt_version` / `policy_version` / `capability_jti` |
| 门禁 | `capability_consumed`、`idempotency_keys` | `jti` 主键实现一次消费；幂等键存 `result_json` |

> 已知迁移点：`main.py::SCHEMA` 的 `conversations` / `messages` 建表 SQL 未含 `tenant_id` 列，但 INSERT 已带该列，须先跑 `scripts/migrate.py` 的 `ALTER TABLE` 补列（并创建 `anonymous` 虚拟用户与种子账号）。`lifespan` 与 `scripts/deploy.sh` 均未自动调用该迁移。

### 6.3 数据契约

| 字段 | 语义 | 规则 |
|---|---|---|
| `valid_from` / `valid_to` | 业务发生时间与有效期止 | 电话改条件的时刻，不从文件名推断 |
| `system_received_at` | 系统接收时间 | 补录时刻，与业务发生时间分离 |
| `confirm_status` | 未确认／已确认／已作废 | 与时间轴正交的独立字段 |
| `invalidate_reason` | 作废原因 | 作废记录必须保留 |
| `confirmed_by` | 确认人 | 跨团队变更须登记责任人，未确认项不挂对方名下 |
| `source_ref` | 来源位置 | 文件路径 + 原文字符区间，供点击回溯 |

版本有效 = 有效期 **AND** 确认状态双条件同时成立；过期来源不得覆盖已确认新版本；读取失败保留上次快照并标记时间，提示人工核查。

### 6.4 状态机

```text
IDLE → EVIDENCE_CHECKED → DRAFT_CREATED → COMPLIANCE_CHECKED → SUBMITTED
  └────────────────────→ ESCALATED（材料不足 / 超时 / 制度未覆盖）
```

| 写工具 | 允许的前置状态 | 目标状态 |
|---|---|---|
| `create_confirmation_draft` | `EVIDENCE_CHECKED` | `DRAFT_CREATED` |
| `validate_policy_compliance` | `DRAFT_CREATED` | `COMPLIANCE_CHECKED` |
| `submit_confirmation` | `COMPLIANCE_CHECKED` | `SUBMITTED` |
| `escalate_case` | 任意非终态 | `ESCALATED` |

跃迁由 `AgentDB.set_state()` 在同一把锁内改状态并写 `case_events`。`confirmation_cases.state` 仅冗余展示。`CLOSED` / `REJECTED` 只由管理员后台产生，状态机与工具集均未定义跃迁。

### 6.5 审计与日志模型

| 表 | 粒度 | 关键字段 |
|---|---|---|
| `agent_rounds` | 一轮决策一行 | `decision_type`、`tool_names`、模型 `latency_ms`、tokens、版本号 |
| `agent_tool_calls` | 一次工具调用一行 | 工具名、**脱敏参数**、`latency_ms`、240 字结果摘要、`error_code`、`capability_jti` |
| `audit_flags` | 一次预筛命中一行 | `suspected`、命中规则、理由、复核人与时间 |
| `audit_logs` | 一次管理／门禁动作一行 | 动作、目标、详情、操作人、IP |

三条纪律：先落日志再执行工具；失败调用也留痕（否则成功率虚高）；门禁拒绝单独标 `gate_rejected`，作为「提示词是否被注入攻破」的观测探针。`safe_params()` 对含 token/password/secret/api_key/authorization 的键替换为 `sha256[:8]` 指纹。日志保留矩阵（对话 180 天、决策与工具日志 365 天、审计 ≥3 年）**尚未落地，属 P0 阻塞**。

## 7. 接口设计

### 7.1 鉴权

`JWT_ALGORITHM=HS256`、`JWT_EXPIRE_HOURS=12`；载荷固定 `sub`(user_id)、`tid`(tenant_id)、`rol`(role)、`unm`(username)、`iat`、`exp`、`jti`。登录写 `httponly` + `samesite=lax` Cookie（`max_age=43200`），也支持 `Authorization: Bearer`。

`get_current_user()` **每次请求回查 DB** 校验 `is_active` 与 `user["tenant_id"]==payload["tid"]`，且不信任 JWT 里的角色（防令牌跨租户复用、停用后旧令牌立即失效）。`require_user()` 任意已登录；`require_admin()` 校验 `role=="admin"`。`tenant_id` 只从 JWT 注入，**绝不接受请求体／查询参数**。

### 7.2 统一错误体与错误码

`{code, message(中文), detail, request_id}`，`_HTTP_STATUS` 显式映射 400/404/403/429/503/504/500。

| 类别 | 码 |
|---|---|
| 请求 | `40001` INVALID_JSON、`40002` MISSING_QUESTION、`40003` EMPTY_QUESTION、`40004` QUESTION_TOO_LONG(500 字)、`40005` BAD_SESSION_ID |
| 会话 | `40101` SESSION_NOT_FOUND、`40301` FORBIDDEN_SESSION |
| 限流 | `42901` RATE_LIMITED |
| 服务 | `50001` INDEX_NOT_READY、`50002` RETRIEVAL_FAILED、`50003` LLM_UNAVAILABLE、`50004` LLM_TIMEOUT、`50099` INTERNAL_ERROR |
| 框架 | `40401` / `40501`；鉴权 `40110`–`40312` 等 |

### 7.3 路由分组（27 条，契约见 `tests/check_routes.py`）

| 组 | 路由 |
|---|---|
| 公共／员工 | `GET /`、`GET /health`、`GET\|POST /login`、`GET /logout`、`POST /chat`、`GET /api/sessions/{sid}/messages` |
| 用户管理 API | `GET /api/admin/users`、`POST /api/admin/users`、`POST /api/admin/users/{id}/reset-password` |
| 知识库 | `GET /admin/knowledge`、`POST /admin/knowledge/upload`、`POST /admin/knowledge/reindex`、`GET /admin/knowledge/documents/{id}/chunks`、`POST /admin/knowledge/documents/{id}/delete`、`GET /api/admin/kb/documents`、`DELETE /api/admin/kb/documents/{id}` |
| 提示词 | `GET /admin/prompts`、`POST /admin/prompts/save`、`POST /admin/prompts/rollback` |
| 对话审计 | `GET /admin/audit`、`POST /admin/audit/flags/{id}/review` |
| 后台页面（SSR） | `GET /admin`、`GET /admin/users`、`POST /admin/users/create`、`POST /admin/users/{id}/toggle`、`POST /admin/users/{id}/reset-password` |

`check_routes.py` 含 `CODE_IN_COMMENT`、装饰器、handler、模板四类静态守卫，`test_core.py` 断言路由数 ≥27，防止「注释吞代码」静默丢路由。

### 7.4 SSE 协议

帧格式 `event: X\ndata: {json}\n\n`（`ensure_ascii=False`）；响应头 `Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no`。

```text
meta → status(retrieving) → citations → status(generating) → delta* → done
任一环节失败 → error（此后不再发其他事件）
```

- `meta` 实际字段为 `{session_id, message_id, is_new_session}`（注意 `api.md` 中写的 `{session_id, request_id}` 与代码有出入，以代码为准）。
- `done` 带 `usage` / `latency_ms` / `citation_check`。
- 算法层 `RAGEngine.stream_chat()` 只发 `citations → delta* → done`，`meta` / `status` 由接口层补；同步生成器经 `aiter_sync_gen()` + 8 线程池跨线程队列搬运。
- 流中断时前端必须标注「回答未完成，请勿据此办理」并给出重试／转人工入口，不允许空白气泡或永久转圈。

### 7.5 Agent 工具 schema 规范

9 个工具：只读 4 个（`list_my_exceptions`、`get_exception_detail`、`lookup_policy`、`get_case_state`），校验签发 2 个（`validate_evidence`、`validate_policy_compliance`），受门禁写操作 2 个（`create_confirmation_draft`、`submit_confirmation`），安全动作 1 个（`escalate_case`）。

`admin_review` / `export_settlement` / `close_case` / `reject_case` **根本不定义**——不暴露就不可能调用。工具 schema 不含身份字段。

## 8. 安全与权限设计

### 8.1 多租户隔离

以**用工单位**为隔离边界；派遣公司跨租户只读监管；员工仅本人数据。所有 `AdminDB` 对外方法第一个位置参数固定 `tenant_id`，SQL `WHERE` 以 `tenant_id` 打头；`AgentDB` 查询带 `tenant_id=? AND user_id=?`；`KnowledgeBase._indexes[tenant_id]` 每租户独立索引；会话恢复先判租户再判归属，非管理员只能读本人会话；启动时 `_check_tenant_orphans()` 自检孤儿租户分区。跨租户访问一律 403／404 且不泄露资源存在性（AC-27 遍历全部 27 条路由验证）。

### 8.2 四层能力边界

| 层 | 机制 | 保证 |
|---|---|---|
| L1 工具暴露面 | 按角色裁剪 tools 白名单 | 管理动作根本不在员工 Agent 工具列表 |
| L2 服务端状态机 + 能力令牌 | 7 项校验的一次性 HMAC 凭证 | 跳步、伪造、复用、参数漂移、跨租户均不产生业务后果 |
| L3 幂等 + 全量审计 | 幂等键、决策日志、工具日志、`gate_rejected` 标记 | 可回滚、可追责、可观测 |
| L4 系统提示词 | 强制段代码写死 + 运行时状态卡 + 可编辑正文 | 只改善效率与话术，**不承担正确性** |

### 8.3 注入防御与内容安全

现有：强制段不可被正文段覆盖；只扫提问不扫回答；拒答白名单；门禁独立于提示词。

待补（P0）：`injection` 类预筛规则，覆盖「忽略之前的指令」「忽略上述规则」「系统提示词」「扮演」等特征；间接注入（员工备注、上传的制度文档）埋点检测；回复不复述规则原文、不泄露 token；提示词版本回滚演练（AC-28、AC-29）。

### 8.4 限流与配额

`RateLimiter(max_calls=20, window_sec=60)` 为**进程内**滑动窗口（`dict[key→list[float]]` + `threading.Lock`），键 `user:{user.id}`，超限 `42901`。实测前 20 次 200、第 21 次 429。多 worker 不共享，部署侧需换 Redis（接口 `check(key) -> bool` 已按可替换设计）。待补：租户日调用上限、月度 token／费用告警、超额不发起 LLM 调用（NFR-06 / AC-38）。

### 8.5 密钥与 dev_mode

`JWT_SECRET` 默认 `dev-only-change-me-in-production`；`AGENT_GATE_SECRET` 缺失时进入 `dev_mode`。`config/default.yaml` 声明「缺失必需密钥即拒绝启动」，但**代码内强校验尚未实现**，仅 `scripts/deploy.sh` 做启动前兜底检查。生产须由密钥管理服务注入，`dev_mode` 禁用，TLS 由反代终止（AC-34）。

## 10. 部署与运维

### 10.1 环境与依赖

`pyproject.toml` 声明 Python `>=3.11`；CI 只在 **3.13** 验证（历史坑：`numpy==2.5.3` 要求 ≥3.12，3.11 失败）。3.11 环境建议 `pip install -e .` 自行解析依赖，不用固定 `requirements.txt`。`config/default.yaml` 当前**不会被程序自动加载**，全部配置走环境变量。

### 10.2 启动

```bash
export PYTHONPATH="$PWD/src"
python -m uvicorn attendance_agent.main:app --host 127.0.0.1 --port 8000
# 或：python -m attendance_agent.main
```

关键环境变量：`DB_PATH` / `DOC_PATH` / `INDEX_DIR`、`JWT_SECRET`、`AGENT_GATE_SECRET`、`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`、`EMBED_PROVIDER`、`HOST` / `PORT`。`scripts/deploy.sh` 启动前预检必需密钥。新库须先跑 `scripts/migrate.py` 补 `tenant_id` / `flag_status` 列。

### 10.3 自检与 CI

`PYTHON=<已装依赖解释器> bash scripts/build.sh` 共 7 步：全量 Python 语法检查、运行依赖预检、27 条路由完整性、30 条评测用例集合法性、核心单测、Agent 三轨迹 + 8 条硬门禁单测、页面与静态资源检查。GitHub Actions 在 Python 3.13 上运行同一套自检（早期 run `42150647198` success）。

### 10.4 备份与回滚

SQLite 用 `Connection.backup()` 在 WAL 有写入时做一致性备份，目标每日自动、异地保留 ≥7 天；每个迁移须有 down 脚本或书面规定「唯一回退路径为备份恢复」并写入 runbook。上线后 30 分钟内 5xx 率超阈值须能按书面阈值、决策人、逐步命令完成回滚演练（AC-35、AC-36、AC-41）。

## 13. 风险、已知缺陷与待决项

### 13.1 上线检查清单结论

25 项检查中 **12 项 P0 阻塞**、7 项 P1 需书面补偿方案。三项必须在放行前关闭：密钥仍为开发默认值、无任何日志保留策略、无代码版本基线／无可用回滚制品。结论：**当前不具备上线条件**。

### 13.2 已登记缺陷 D-01~D-06

| 编号 | 缺陷 | 级别 |
|---|---|---|
| D-01 | 预筛漏「伪造发票」等同义改写；`injection` 类规则缺失，注入句静默放行 | P1 |
| D-02 | 离线 MockLLM 回显提示词前 300 字 | P0（演示版） |
| D-03 | 限流为进程内，多 worker 不共享 | P0 |
| D-04 | 引用编号只查越界，「编号未越界但指错块」抓不住 | P1 |
| D-05 | 两套制度知识源（`报销制度.md` RAG 与 Agent `POL-*`）章节号冲突，`make_rag_policy_lookup()` 签名不适配会静默回退 demo 片段 | P1 |
| D-06 | Agent Harness 未接入主聊天链路，`/chat` 只走 RAG | P0 |

### 13.3 其他已知边界

- `main.py` 不 import 任何 `agent_*` 模块；Agent 仅由 `examples/demo.py` 离线演示。
- `ESCALATED` 之后「谁处理、多久处理」SLA 未给出，属悬空终态；超时自动升级的定时作业代码中未找到。
- 完整后台复核队列、`CLOSED` / `REJECTED` 跃迁与管理工具未实现。
- `config/default.yaml` 不被自动加载；`audit_flags` 无 `injection` 分类。
- 归档 MVP：匿名无隔离、无后台／Agent／审计、`MockLLM` + 纯 BM25 的回答质量不代表线上。

### 13.4 待决项 Q-01~Q-10

口头变更是否一律未确认（阻塞 W3）、授权确认人清单（阻塞 W3 审批）、无统一编号时的替代比对键（阻塞 W1）、一页清单字段范围（阻塞 W2 验收）、过期判定口径与人工队列责任人（阻塞 W2）、变更以哪份原始记录为准（阻塞二期）、保留期限与删除触发条件（阻塞上线）、两条业务线是否打通与知识源统一（阻塞二期）、首个客户考勤数据格式与触达通道（阻塞场景 B 上线）、试点批次与骨干名单（阻塞 W1）。完整责任人与影响需求见《需求分析方案 v1.0》§5.3。
