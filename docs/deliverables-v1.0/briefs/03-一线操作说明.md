# 03 · 一线操作说明（Operator）

> 四来源简报包 · 文件 3/4 ｜ 版本 v1.0 ｜ 整理日期 2026-11-06
> 对应视角：Operator · 一线使用者 **林亦舟**（源报告 r1）
> 来源：`docs/discovery-report.md` 访谈记录 00:59:22.203Z ~ 01:00:06.298Z，事实编号 f10~f15
> **性质声明**：操作陈述与异常样本均来自合成演练；「80 个岗位需求、重复澄清 22%」是源报告明确标注的**虚构基线**，不得作为 ROI 输入或效果目标。

## 1. 现状流程与两个时间口径

```
客户提需求 → 岗位条件澄清 → 人员安排确认 → 到岗交接 → 反馈
                  ↑                    ↑
            电话改条件发生       交接单仍引用旧技能要求
```

| 时间类型 | 定义 | 实操表现 |
|---|---|---|
| 业务发生时间 | 条件在电话/群消息中被改动的时点 | 现场先用群消息解决 |
| 系统接收（回填）时间 | 表格被补填的时点 | 晚于发生时间，常滞后几十分钟到数小时 |

关键规则：**回填时间不能当作发生时间**（f13），异常识别若把顺序搞反，会把"先变更后补录"误判成"先有表格后有变更"。系统需同时记录两类时间戳（f34）。

## 2. 最费时间的环节

1. 电话改条件后的逐个核对：确认哪一版才算数；
2. 回头改单子、回填表格；
3. 标记异常、发起人工复核、留痕原值与来源位置。

一线本人**明确拒绝**提供单量与耗时统计：「每单花多久、人工复核平均耗时，我这边没有统计，不能凭印象给数字。」因此本简报不填任何工时估计值。

## 3. 典型异常样本（合成）

| 项 | 内容 |
|---|---|
| 事件 | 临时增加夜班要求，但已确认到岗的班次没有同步（f11） |
| 关联问题 | 岗位条件在电话里改了，交接单还引用旧技能要求（f10） |
| 必须记录 | 发生节点、受影响对象、原始版本（f10、f11） |
| 处置约束 | 不直接改结论；先标记异常 → 发起人工复核 → 留痕原值和来源位置 |
| 责任判定 | 查原始版本后判断，不由系统推定 |

## 4. 人工复核动作（不可省略）

| 步骤 | 动作 | 依据 |
|---|---|---|
| 1 | 正式闭环前由当班人员核对关键字段 | f14 |
| 2 | 系统建议**不能覆盖原值**，也**不能省略确认** | f14 |
| 3 | 发现错误：标记异常、发起人工复核、留痕原值与来源位置 | f14 |
| 4 | 改单权限与复核边界上报傅景确认 | r1 陈述 |

## 5. 对辅助结果的交付要求

> 「为了减少返工，我需要**一页缺项清单**和对应岗位服务需求单的**来源位置**，不需要一份很长的泛化摘要。」（f15）

| 要求 | 说明 |
|---|---|
| 形式 | 1 页清单，不是长摘要 |
| 必备 | 缺项字段 + 来源位置 |
| 不要 | 泛化摘要、系统替人下结论 |
| 验收联动 | 每条结果关联来源与人工复核记录（f42） |

## 6. 演练基线（虚构，仅用于演练）

| 指标 | 数值 | 声明 |
|---|---|---|
| 模拟岗位需求 | 80 单 | 演练样本 |
| 重复澄清占比 | 22% | 源报告明确标注为虚构数据，不代表真实经营 |

**使用限制**：三档报价与投入产出方案已明确不把 22% 作为 ROI 输入；任何效果浮动在基线未冻结前按 0 计。

## 7. 一线提出的待核实问题

1. 试点只覆盖电话改条件，还是群消息先行的单子也纳入？（不定的话人工复核量无法估）
2. 「错误」指字段填错，还是辅助判断本身判错？两类处理路径不同。
3. 异常识别拆到「发现与标记」层，还是追到「责任归属」层？
4. 试点是否包含夜班不同步这类班次异常？

## 8. 建议的补证动作（G0）

先按现有需求单做一次**小样本计时**，把「发现 / 标记 / 发起复核 / 留痕」四步分开记录，标注为待验证假设；样本量与范围须等顾明岚、傅景确认后再定。计时结果只作为基线候选，不直接充当验收指标。
