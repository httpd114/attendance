## 1. 系统边界

派遣用工场景下，考勤异常（迟到、下班缺卡、加班时长争议）需要**员工与用工单位双向确认**。
系统做三件事：依据制度知识库回答员工疑问、整理并校验确认／异议材料、把确认单推进到管理员复核队列。

明确不做的边界（来自需求清单 v0.1）：

- 系统**不会因超时自动通过**任何异常，超时只升级上报。
- AI **不是审批者**，最多把单据推到 `SUBMITTED`；复核通过／驳回／关闭／结算导出由管理员在后台人工完成。
- 一期**只记录并导出**结算数据，不直连薪资、不开票。
- 多租户以**用工单位**为隔离边界；MVP 为 SaaS，二期支持私有化。

## 2. 四层架构

| 层 | 实现 | 职责 |
|---|---|---|
| 入口层 | `main.py`（FastAPI）、`core/auth.py` | JWT 鉴权、SSE 流、统一中文错误体、限流、页面渲染 |
| 服务层 | `core/kb.py`、`admin_db.py`、`agent_db.py`、`audit_rules.py` | 知识库、会话与用户、确认单状态、审计标记、动作日志 |
| 智能体编排层 | `core/agent_loop.py`、`agent_gate.py`、`agent_tools.py`、`agent_prompt.py` | 模型决策循环、能力令牌门禁、工具 schema 与执行、强制提示词 |
| 数据模型层 | SQLite（WAL）+ FAISS 内存索引 + embedding BLOB | 会话、消息、切片与向量、审计日志、Agent 决策日志 |

当前实现用 SQLite 单文件；设计演进方向是 PostgreSQL + pgvector、Redis 共享限流、对象存储放附件。
`faiss` 索引是**内存派生**的，重启后从 `kb_chunks.embedding` BLOB 重建——删除文档无需再调 embedding API。

## 3. 代码分层与依赖方向

```
src/attendance_agent/
  main.py            → core.* + utils.paths
  core/              → 只允许依赖同层模块与 utils.*，不得反向 import main
  utils/paths.py     → 零业务依赖
```

依赖是单向的。`utils/paths.py` 统一解析「项目根在哪」，避免分层后各模块自己数
`parents[n]` 算错目录，也便于部署方式变化时只改一处。

## 4. 两条主链路

### 4.1 制度问答（`/chat`）

```
提问 → 规则预筛（只标记不定性） → 租户内混合检索 → 提示词组装 → LLM 流式生成
     → 引用编号自检 → SSE 事件流 → 会话与消息落库
```

检索用 BM25 + 中文字符二元组 BM25 + 向量三路 RRF 融合。切片**先按 Markdown 标题切节、
节内再按 500 字细分**——纯滑窗会把多个章节搅进同一块，导致答案串项。
向量路不可信时整体关闭，绝不注入无语义的 Hash 向量伪装成有效检索。

### 4.2 Agent 确认闭环

```
模型决策 → 执行工具 → 结果回填 → 再决策（最多 5 轮）
```

一轮 = 一次模型决策 + 串行执行该批 `tool_calls` + 一次性回填。无依赖的只读工具同轮批量发；
有凭证依赖的写操作天然跨轮（模型只有看到上一轮回填的 token 才知道下一轮带什么）。
第 5 轮仍在调工具时**不发起第 6 次决策**，用规则模板收敛并写 `audit_logs(agent_round_limit)`。

系统消息每轮重建，**运行时状态卡由服务端从数据库生成**，不让模型靠多轮历史推断进度：
历史会被裁剪、被压缩、被注入内容污染，状态卡每轮都是客观事实。

## 5. 关键设计决策

| # | 决策 | 为什么 |
|---|---|---|
| 1 | **正确性靠服务端门禁，不靠提示词** | 提示词挡不住采样随机性、长上下文稀释、间接注入。提示词让模型「通常不跳步」，门禁让「跳步绝不产生业务后果」 |
| 2 | 能力令牌 HMAC 签名、300 秒、一次性 | 校验工具签发，写工具必须回传；7 项校验含 `params_hash`，挡住「顺序合规但内容漂移」 |
| 3 | `jti` 消费放 7 项校验最后 | 否则签名非法的请求也能烧掉合法 jti，形成 DoS |
| 4 | 状态机单一真源放 `attendance_exceptions.agent_state` | 建单之前还没有 case，存两处必然双写不一致 |
| 5 | 提示词分「强制段 + 可编辑正文段」 | 强制段承载引用编号与拒答规则，是可追溯性的技术前提；放开编辑等于允许把系统改成无引用的自由发挥模型 |
| 6 | 提示词回滚 = 生成新版本，不改历史行 `is_active` | 版本号与实际生效顺序永远一致，审计能说清哪一版真正上线过 |
| 7 | 规则预筛只召回、不定性；只扫员工提问 | 系统永不自动判违规；助手复述「虚报」「超标」是正常的，连回答一起扫会让预警量爆炸 |
| 8 | 预筛权重阈值取 2 | 低危词在正常咨询里高频出现，全量推预警会让管理员对预警系统脱敏 |
| 9 | 决策日志用 1:N 两张表 | 「每轮模型耗时」与「每个工具耗时」是两个统计维度，合成宽表会互相污染 |
| 10 | 自建轻量 Harness，不引第三方 Agent 框架 | 9 工具 5 轮用不上状态图／checkpoint；框架越薄，逐轮审计与硬门禁越好插 |
| 11 | `tenant_id` / `user_id` / `role` 不进工具 schema | 从 JWT 注入，模型无从传参，跨租户攻击面直接消失 |

### 状态机

```
IDLE → EVIDENCE_CHECKED → DRAFT_CREATED → COMPLIANCE_CHECKED → SUBMITTED
  └────────────────────→ ESCALATED（材料不足 / 超时 / 制度未覆盖）
```

`SUBMITTED` 是 Agent 权限天花板。工具按角色裁剪：管理员 Agent 只有 4 个只读工具，
`admin_review` / `export_settlement` 根本不出现在任何 tools 列表里——不暴露就不可能调用。

## 6. 日志与审计模型

| 表 | 粒度 | 关键字段 |
|---|---|---|
| `agent_rounds` | 一轮决策一行 | `decision_type`、`tool_names`、模型 `latency_ms`、tokens、`prompt_version` / `policy_version` |
| `agent_tool_calls` | 一次工具调用一行 | 工具名、**脱敏参数**、`latency_ms`、240 字结果摘要、`error_code`、`capability_jti` |
| `audit_flags` | 一次预筛命中一行 | `status=suspected`、规则、理由、复核人与复核时间 |
| `audit_logs` | 一次管理／门禁动作一行 | 动作、目标、详情、操作人、IP |

三条纪律：先落日志再执行工具；失败调用也留痕（否则成功率虚高）；门禁拒绝单独标
`gate_rejected`，作为「提示词是否被注入攻破」的观测探针。`*_token` 只存 sha256 前 8 位。

## 7. 已知风险与演进方向

- **引用编号语义校验**：目前只能查有无与越界，「编号没越界但指错 chunk」抓不住。
  Agent 让制度结论直接进确认单后风险等级上升，建议与 `validate_policy_compliance` 一起补。
- **两套制度知识源**：`/chat` 用 `data/报销制度.md` 的 RAG 库，Agent 演示用内置 `POL-*`
  考勤片段，章节号存在冲突；`make_rag_policy_lookup()` 未适配会**静默回退**演示片段。
  上线前须统一 `chunk_id` 命名空间。
- **限流为进程内滑动窗口**：多 worker 部署需换 Redis 共享计数（接口 `check(key) -> bool` 已按可替换设计）。
- **无日志保留策略 / 无回滚制品 / 默认密钥**：见 `上线前检查清单-派遣考勤异常双向确认-v1.0.md`。
- 下一步业务闭环：考勤异常双向确认流程尚未与问答／后台完全串通；之后是多租户压测与 PostgreSQL 迁移。
