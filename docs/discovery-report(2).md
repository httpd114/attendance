## 需求如何归纳

先从已采集事实形成问题假设，再约定业务结果、范围、失败控制和验收。缺少的来源标记待补，不能把六人访谈完整率当作四来源收敛或需求确认。

### 业务流程拆解

要回答：问题发生在哪一步，为什么要这样划分智能体？

1. 先画人工现状泳道，写出触发、输入、8–15个处理步骤、交接和异常。
2. 区分判断点与执行点；按使用的数据、权限、模型能力与失败方式组合执行步骤。
3. 在不可逆动作前设置确定性校验；为低置信、缺资料、冲突和越权安排具名人工接收人。

交付链：现状流程 → 失败方式 → 智能体/工具边界 → 校验与人工升级路径

原文：frameworks/workflow-decomposition.md

### 业务结果与不可逆风险矩阵

要回答：多个需求中，先做哪个最小可验证方案？

1. 列出3–5个候选切入点，分别说明改善的业务结果、现状基线和投入。
2. 评估失败何时被谁看见、能否在损害前拦截、是否可以撤销；不要把模型置信度等同于业务风险。
3. 优先选择高价值、可拦截且可恢复的切入点；高风险需硬约束和责任人否决权，价值或风险未知先补证据。

交付链：候选方案 → 价值/风险比较 → 选择与暂缓理由 → 验收指标与停止条件

原文：frameworks/outcome-risk-matrix.md

### 四来源收敛

要回答：谁说要做，哪里真的坏了，范围允许什么，技术是否可行？

1. Buyer：核实业务目标、预算、优先级和决定权；Operator：用最近一单还原真实操作和失败位置。
2. Brief：核对书面目标、范围、时间和排除项；Industry：寻找可比技术实践，并核实本项目的数据与接口差异。
3. 检查四个视角是否指向同一瓶颈。分歧保留在问题清单：一线帮助定位故障，决策者确认价值，Brief约束范围，行业证据帮助判断可行性。

交付链：四视角陈述与来源 → 收敛/分歧 → 待核实问题 → 有边界的需求假设

原文：frameworks/4-source-convergence.md

### 从证据到候选需求

- REQ-1 需求单版本与交接单版本未对齐是核心瓶颈，需建立变更触发与版本引用规则
  依据：fsg-assignment-f01、fsg-assignment-f02
  推导：f01确认链路含条件澄清与到岗交接两个交接点，f02要求变更有影响清单，说明变更留痕是验收底线；但受访者明确表示电话改条件后由谁触发版本更新、多久内完成尚未核实，也无证据证明交接单当前引用哪一版本。瓶颈定位在交接点而非单点操作，属推断。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：抽取一个批次内3至5个发生过电话改条件的岗位，逐条比对需求单版本与交接单引用版本，记录差异与触发人；由业务与交接双方书面确认触发责任人与时限，作为验收前置条件。
- REQ-2 减少重复核对需先定位具体环节与确认人，否则价值无法验收
  依据：fsg-assignment-f00、fsg-assignment-f02
  推导：f00明确目标为减少重复核对且不丢人工确认与来源，但受访者自述减在哪个环节、由谁确认减到位尚未核实。缺少环节级基线，验收只能停留在纸面。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：在试点批次内按f01链路逐点记录现有核对动作、次数与执行人，形成基线清单；由业务负责人确认拟削减项，质量负责人确认保留项，双方签字后方可作为验收依据。
- REQ-3 异常识别后的人工复核责任人未定，质量叫停权缺少触发口径
  依据：fsg-assignment-f04、fsg-assignment-f02
  推导：f04确认质量侧保留停止试点权利，f02要求变更留影响清单，但受访者指出异常识别后复核责任人及叫停触发条件均未核实。责任空缺会使叫停权无法执行，属不可逆风险点。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：由质量负责人牵头列出异常类型与对应复核岗位、响应时限及叫停条件草案，经业务负责人确认后写入试点方案；未确认前不扩大试点范围。
- REQ-4 试点范围应收窄至单批次并禁止真实人员安排，作为风险隔离前提
  依据：fsg-assignment-f05、fsg-assignment-f03
  推导：f05已明确单批次、不自动决定录用派遣、不向真实人员发送安排；f03限定四周两名骨干每周不超四小时。范围与资源约束已有事实支撑，但批次选取标准与骨干人选尚未核实。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：由业务负责人书面指定试点批次与两名骨干名单，确认每周四小时上限的执行记录方式；超出即按f03重新评估，不默认扩容。
- REQ-5 成本仅能按人时记录，工时折算规则缺失限制金额结论
  依据：fsg-assignment-f03
  推导：f03给出投入上限，受访者称按工时核算、不引入采购，但工时如何折算成本、由谁出账尚未核实，且财务视角未采集。因此验收阶段只能提供投入记录，不能给出金额结论。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：先按人时做简账记录四周投入；就折算规则向财务口径负责人发起一次确认访谈，取得书面口径前不将成本金额列入验收指标。
- REQ-6 客户侧结果用途确认时点未定，影响试点结果能否对外使用
  依据：fsg-assignment-f04
  推导：f04确认客户协同代表约束结果用途，但确认时点尚未核实，客户视角亦未访谈。若用途确认滞后，试点产出可能无法用于对外沟通，但不影响内部验证。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：向客户现场负责人确认结果用途的确认时点与形式，写入试点方案；在确认前，试点产出仅限内部使用。
